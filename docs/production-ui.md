# Production Trip UI

The root Worker now serves the approved React UI, built by Wrangler's custom build command. The production entry uses native scrolling, inputs and responsive sheets, with no device frame or simulated keyboard. The reference prototype is retained separately.

Production trip data comes from authenticated `/api/app/*` handlers using the authoritative `TRIP_DB` Cloudflare D1 binding. Existing KV data is read-only migration input. Legacy fields remain stored; new planner, packing, booking, clothing and Whitepages content is stored under each record's `ui`. Trip access is owner/shared-account scoped. Only trip owners can change sharing; explicit Editor access permits edits. Private packing/photos are user scoped; shared item progress is updated only for the authenticated user. Weather calls Open-Meteo. Scanner output requires review and does not automatically save a trip.

The existing login compatibility fallback remains active when `TRIP_AUTH_USERS` is absent. Configured accounts override that fallback. Existing Gabe/Lux owner accounts manage integrations by default only when `TRIP_ADMIN_USERS` is unset; explicitly configured admin lists take precedence. `TRIP_KEYS_ENCRYPTION_KEY` remains supported. Without it, the existing private `trip_agents` R2 binding initializes an encryption master with a conditional create-only write under `private/trip/keys-master-v1`; group credentials are encrypted in D1. The public agent-file API does not allow access to this private path. Master keys never return to browsers.

Account → Connections lets owners add/test keys, edit prompts and approve groups. Actual provider credentials are still required for Sonar/Firecrawl/Apify. Unconfigured or failing providers return explicit errors. Flight tracking has no authoritative provider connected and displays unavailable rather than generated live status. Maps directions open explicitly in a separate page.

Validation: `node scripts/build-production.mjs` followed by `node --test tests/*.test.mjs` passes 140 tests, including production routing, legacy login compatibility, trip access/personal data isolation, provider group policies, encryption bootstrap and scanner review. Browser QA with isolated accounts verified server packing persistence through reload. These are not claims of successful paid provider requests or real-account sign-in.

D1 revision checks reject stale trip saves instead of overwriting newer records. Integration settings retain a group document update model; simultaneous owner edits still require care. Migration preserves legacy and unowned records without reassigning them; KV is retained as a backup.

## Focused UX and rich AI outputs

Sign-in now loads trips immediately. Planner includes a compact date strip, calendar counts, trip-wide Events and visible time-overlap indicators. Packing supports editing/removing items and filtering unfinished items; Mine/Shared progress uses the selected bucket. Scan review keeps manual corrections across retries, highlights missing details, and offers manual entry. Desktop scan review places the image beside fields. Sharing lists per-member role/revoke controls and distinguishes trip access from integration-key approvals.

Trip AI renders short formatted answers, source URL cards and opt-in image cards with source-page attribution. Research datasets render bounded cards instead of raw JSON. The conversation remains when switching agents; changing the connection/account clears it. Account → Connections → Image search selects Firecrawl, a configured Apify Actor, or Off. Google Images requires an appropriate Apify Actor and its JSON input template; no Google scraping credentials or paid Actor is silently provisioned. Members require approval for the selected media provider separately from Sonar. Images are loaded from provider-returned public HTTPS URLs without sending a referrer; failures leave a source link/text fallback. Preview metadata comes from provider results; the Worker does not fetch arbitrary preview destinations.

Image lookups are opt-in and capped at six images. Apify research reuses the same dataset for image results when selected, avoiding a duplicate paid run. Provider responses are limited to 1 MiB. Failed image lookups retain the answer and explain the error. Current-session 401s clear expired credentials; a late 401 cannot clear a newer session. Connection tests preserve settings saved while a test is pending and reject results for a replaced key.

Validation for this update: 140 backend/client tests pass, production TypeScript/Vite build and 28-file runtime integrity check pass. Isolated browser QA exercises planner, packing persistence/filter totals, sharing revocation and rich AI cards at desktop and a 390×844 iframe viewport. Provider responses in browser QA are fixtures; successful real-account sign-in, paid provider calls and real booking OCR remain unverified.

## D1 registry, Map and Events

The `TRIP_DB` binding is the authoritative registry. `page_registry` defines seven whitelisted pages and their navigation order: the five existing buckets plus `/map` under Travel and `/events` under Planner. Unknown renderer/path combinations cannot execute code. Deep links retain the selected trip/date and support browser history.

`trips` stores individual trip documents with numeric revisions; indexed `trip_acl` rows scope reads and sharing. Saves use revision comparison and atomic SQL batches so a stale save cannot overwrite newer trip data or ACLs. Conflicts ask the user to refresh. `app_records` stores encrypted integration settings and expiring sessions. Existing KV records are read-only migration input: trip import and its completion marker commit together, and each session/settings key migrates once with tombstones preventing stale session resurrection. The old KV backup is not deleted or written. Required-D1 production mode returns503 rather than silently falling back to KV.

Private image data URLs are deduplicated into the existing private R2 bucket; D1 stores scoped references and metadata. Authenticated trip reads hydrate those images under the existing ownership/private-item rules. Images belong in object storage to stay below D1 row limits. Failed migration keeps the legacy backup and does not mark import complete.

Map uses saved destination coordinates or a real destination lookup, saved activity places, and day-route links. Stops without confirmed coordinates are not given invented markers. Events reuses itinerary activities: Find events searches using the saved destination/date, and Import link extracts a prefilled draft through the user's approved Firecrawl connection. Search snippets do not create invented dates or times; unknown times remain unscheduled. A user reviews and saves each imported draft, retaining its source link. These functions do not make bookings.

Wrangler auto-provisions the named `TRIP_DB` database on deploy; IDs need not be committed to the repository. Runtime schema initialization and one-time legacy import are idempotent. `keep_vars` preserves existing dashboard variables. Successful deployment must be followed by a production `/api/health` response reporting `storage: d1`; build success alone does not establish database readiness.

Map verification uses Leaflet raster tiles (no WebGL) from OSM Deutschland with provider attribution. The standard OSM tile endpoint returned a policy-block image in the QA browser and is not used. External directions remain available if the volunteer tile service is unavailable. Backend validation now passes 140 tests, including 26 real SQLite D1 tests and nine import/discovery tests.

## Discovery actions and trip history

The Events registry page now opens Discover, with Places, Trails and Events search categories. Search results retain their source links and persist as trip-scoped recommendations under `ui.discoveries`. Dismissed recommendations stay hidden across repeated searches and reloads; Hidden restores them. Mark visited records an explicit selected visit date in trip history. Linked saved activities share visited state with the corresponding recommendation. Saved plan, History and Hidden views remain separate from the primary five navigation buckets.

Each recommendation can open Maps, prefill an activity for review, or read source details through the existing approved Firecrawl connection. Source-provided valid coordinates survive import and activity edits; the map displays confirmed coordinates only. The map fits its saved markers, lets travelers select a trip day and opens discovery from its search action. A web search result is not a verified place database record: source details, opening hours and trail/event conditions require checking.

Activity review includes a trip-day chooser and Find a free slot. The deterministic suggestion uses a configurable time window (09:00–20:00 by default), the visit duration and a 15-minute buffer on either side of existing activities. It never moves existing plans, including fixed reservations. Unknown scheduled activity times block fitting rather than claiming a free interval. Suggestions must be explicitly saved. The buffer is not a calculated travel-time estimate, and opening hours are not checked automatically.

Validation for this change: production TypeScript/Vite build and 28-file runtime integrity check pass; 152 automated tests pass, including source import, category search, dismissal/history persistence, permissions, D1 revision conflicts and scheduling gaps. Interactive visual acceptance remains unverified: the available cloud browser could not reach the isolated local fixture (`net::ERR_CONNECTION_REFUSED`). Live provider responses, production deployment and real-account acceptance are not established by these checks.
